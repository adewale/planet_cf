# Planet CF — Full Re-Audit

**Date:** 2026-06-13
**Baseline:** commit `74a77e6` (main, 2026-04-12)
**Scope:** all of `src/`, `docs/`, `README.md`, `TODO.md`, `tests/`, `scripts/`, `migrations/`, `examples/`, wrangler configs, CI workflows, Makefile, static assets
**Method:** six parallel domain deep-dives (security, core correctness, docs accuracy, test quality/CI, deployment/infra/scripts, frontend/templates), each cross-checked against the running code; the lead auditor independently re-verified every High finding by reading the cited code and/or executing the relevant commands. The full unit+integration suite, ruff, ruff-format, ty, vulture, and vitest were executed as part of this audit.

---

## Executive summary

The two fix rounds after the 2026-03-11 audit were real: most prior code-level findings are genuinely fixed, the core security controls hold (parameterized SQL throughout, constant-time HMAC sessions, OAuth `state` checking, XML escaping with CDATA-breakout protection, strict CSP on HTML pages, no committed application secrets), the working tree passes ruff/format/vulture cleanly, and 1,426 unit+integration tests pass deterministically with 88% branch coverage.

This re-audit nonetheless found **0 Critical, 15 High, ~20 Medium** issues, concentrated in four clusters that previous audits under-examined:

1. **The feed pipeline has correctness bugs in its hottest path.** The entry upsert cannot distinguish inserts from updates (`RETURNING id` fires on both), so every entry of every changed feed is re-embedded into Vectorize hourly, `last_entry_at` is overwritten with the *oldest* entry of each fetch, and the "entries added" signal is meaningless (H1). New ETags are persisted before entries are stored, so a mid-fetch timeout permanently loses entries behind a 304 (H2). System audit-log writes violate a foreign key D1 enforces, so any redirecting feed throws mid-cycle (H3).
2. **Parts of the admin UI and feed output are visibly broken in production.** The site's own CSP kills every inline handler: the Reindex button does nothing and feed deletion happens *without* its confirmation dialog (H4). The health page's Activate/Deactivate buttons and the dashboard's DLQ Retry button hit endpoints that return 405 (H6). RSS subscribers see raw HTML markup as text because autoescape entity-encodes inside CDATA (H5). The health page always shows "Last Entry: Never / Entries: 0" because the row factory drops SQL-computed columns (M6).
3. **The onboarding and deploy paths do not work as documented.** The README quickstart cannot produce a working instance (resource-name mismatch, single-migration schema gap, empty crons, circular `make python-modules`, missing test extra) (H9, H14). `deploy_instance.sh` re-runs abort silently due to a `set -e` interaction (H10). CI's migration step can never fail and deploys to production regardless (H8b). The lite-mode feed-management workflow documented in `docs/LITE_MODE.md` does not exist in the code at all (H13).
4. **The quality gates give false confidence.** CI's unpinned `ty` now fails on main, so the next CI run is red (H8a). The JS test suite fails 10 of 27 tests, tests an unserved copy of `admin.js`, and is wired into no CI step (H7). The E2E suite turns into "107 skipped, exit 0" when no live deployment answers (M9). The coverage gate is timing-flaky under instrumentation (M8).

Security posture is unchanged at its ceiling: still no CSRF tokens on state-changing admin endpoints (the headline open finding from March), plus new Medium defense-in-depth gaps (feed-controlled `javascript:` hrefs blocked only by CSP; SSRF re-validation that runs after the request; an XXE control that regressed from `forbid_dtd` to a regex). Two trust/operational hazards stand out: `migrations/002` seeds the upstream maintainer as an active admin on every third-party deployment (H11), and a deterministic committed `SESSION_SECRET` protects a deployed, full-mode, publicly routable test worker (H12).

## High findings

### H1. Entry upsert treats every update as an insert — hourly re-embedding, corrupted `last_entry_at`, meaningless stats
**Area:** pipeline correctness · `src/main.py:1201-1253` · *lead-verified*

The upsert uses `ON CONFLICT(feed_id, guid) DO UPDATE SET … RETURNING id`. In SQLite/D1, `RETURNING` fires for the `DO UPDATE` branch too, so `entry_id` is truthy for **every** entry on **every** 200 response. Consequences:

- `last_entry_at` is rewritten once per entry (`main.py:1235-1245`); feeds list newest-first, so after each fetch it holds the **oldest** processed entry's date — the opposite of migration 004's intent — and updates even when nothing new arrived. Stale-feed detection via this column is impossible.
- `_index_entry_for_search` runs for every entry on every fetch (`main.py:1253`): a feed without conditional-GET support and 100 retained entries costs ~2,400 Workers-AI embedding calls + Vectorize upserts per day, forever.
- `entries_added == entries_found` in events, logs, and the fetch-now JSON.

**Fix:** make the insert distinguishable (e.g. add `WHERE` to the `DO UPDATE` so it only fires on real content change, or `RETURNING id, (updated_at IS NULL) AS inserted`); set `last_entry_at` once after the loop from `MAX(published_at)`; index only on insert/changed content.

### H2. New ETag/Last-Modified persisted *before* entries are stored — mid-fetch failure becomes permanent silent entry loss
**Area:** pipeline correctness · `src/main.py:1111`, `1561-1562` vs `1159` · *lead-verified*

`_update_feed_metadata` unconditionally writes `etag = ?, last_modified = ?` before the entry loop runs; `_update_feed_success` writes them again after. If the loop dies mid-way (e.g. a large feed deterministically exceeding `FEED_TIMEOUT_SECONDS` — the code's own comments cite pythonbytes.fm), the new validators are already stored: the next cycle's conditional GET returns **304**, which is treated as success (`main.py:1085-1087`) and even resets `consecutive_failures`. The unsaved entries are never fetched again and the feed reports healthy forever.

**Fix:** drop the validator columns from `_update_feed_metadata`; they belong only in `_update_feed_success` after all entries are stored.

### H3. System audit-log writes bind `admin_id = 0`, violating a foreign key D1 enforces — every redirecting feed errors mid-cycle
**Area:** pipeline correctness · `src/main.py:1508-1518`, `3796`; `migrations/001_initial.sql:84` · *lead-verified*

`_update_feed_url` logs the URL change with `.bind(0, "url_updated", …)` into `audit_log.admin_id`, which has `FOREIGN KEY (admin_id) REFERENCES admins(id)`; no admin row with id 0 exists (002 seeds `adewale` with autoincrement id 1 — its `github_id=0` is a different column), and D1 enforces foreign keys by default. Verified against SQLite: the insert raises `FOREIGN KEY constraint failed`; `NULL` is accepted (the column is nullable). So a feed whose stored URL 301s gets its URL updated, then throws: `_record_feed_error` + 3 queue retries ⇒ **+4 consecutive failures, a DLQ entry, a misleading `fetch_error`, and entries delayed a cycle** per redirect event. `_log_admin_action`'s `None → 0` coercion (`main.py:3796`) has the same problem for any future system-attributed action. Unit tests codify the buggy behavior because `MockD1` doesn't enforce FKs.

**Fix:** bind `None` for system actions (SQL NULL passes the FK); remove the `None → 0` coercion; optionally seed a real "system" admin row.

### H4. CSP blocks all inline JS the templates rely on: dead Reindex button, **unconfirmed feed deletion**, dead mozilla date script
**Area:** frontend/admin · `src/utils.py:205` (`script-src 'self'`); `src/templates.py:375, 437, 694, 1226-1245, 1322-1341` · *lead-verified*

`DEFAULT_CSP` allows inline *styles* (`style-src … 'unsafe-inline'`) but not inline *scripts*, and the admin templates use inline handlers:

- `onclick="rebuildSearchIndex()"` on the Reindex button — `admin.js` attaches no listener to it, so **the button does nothing**.
- `onclick="return confirm('Delete this feed?')"` on Delete (dashboard and health page) — blocked, so the form submits **immediately without any confirmation**: a destructive action lost its only guard.
- planet-mozilla's date-localization `<script>` blocks never execute.

The browser E2E suite only covers public pages, which is why this shipped. **Fix:** move handlers into `admin.js` (`addEventListener` on `#reindex-btn`; a `submit` listener for confirmation) and ship the mozilla script as a static file.

### H5. RSS 2.0 / RSS 1.0 descriptions are entity-escaped *inside* CDATA — readers display raw HTML as text
**Area:** feed output · `src/templates.py:1453, 1481, 1592`; `src/main.py:2358-2366` · *lead-verified (mechanism); agent-verified (rendered output)*

The Jinja environment has `autoescape=True` for all templates including XML. The RSS templates wrap content as `<description><![CDATA[{{ entry.content_cdata }}]]></description>` where `content_cdata` is a plain `str`, so autoescape entity-encodes it **inside** the CDATA: `<![CDATA[&lt;p&gt;Hello &amp;amp; world&lt;/p&gt;]]>`. CDATA suppresses entity decoding, so conforming feed readers show literal `&lt;p&gt;` / `&amp;` text. This also makes the careful `]]>`-breakout escaping at `main.py:2358` dead weight.

**Fix:** mark the payload `markupsafe.Markup(...)` after the `]]>` escape (two call sites), or drop CDATA and rely on autoescape consistently.

### H6. Admin controls wired to endpoints that 405: health-page Activate/Deactivate and dashboard DLQ Retry
**Area:** frontend/admin · `src/templates.py:691-701`; `src/main.py:2923-2931`; `assets/static/admin.js:71` vs `src/main.py:2942` · *lead-verified*

- Health page posts forms with `_method=PUT` to `/admin/feeds/{id}`, but the POST handler only honors `_method == "DELETE"` and returns `{"error": "Method not allowed"}` 405 otherwise (and `_update_feed` reads JSON, not form data). Clicking Activate/Deactivate navigates to a raw JSON error; feed state never changes.
- `admin.js` builds the DLQ retry URL as `/admin/feeds/{id}/retry`; the real route is `/admin/dlq/{id}/retry`. The request falls into the generic POST branch → 405. (The health page's retry form uses the correct path; only the JS is wrong.)

**Fix:** handle `_method=PUT` with form fields (or point the buttons at the existing `/toggle` JSON endpoint); correct the URL in `admin.js`. Add admin-page E2E coverage.

### H7. JS test suite: 10/27 failing, tests an unserved file, runs in no CI step
**Area:** tests/CI · `tests/js/admin.test.js`; `package.json`; `.github/workflows/check.yml` · *lead-verified (ran vitest)*

`npx vitest run` → **10 failed | 17 passed**. The tests import `../../static/admin.js` — the top-level `static/` copy, which no wrangler config serves (`assets.directory` is `./assets/` everywhere); it exists only as a copy-source for `create_instance.py`. The mocks predate `admin.js`'s `if (!r.ok) throw` error handling, so every success-path test takes the catch branch. No CI step or Makefile target runs vitest, so the suite rotted invisibly while `package.json` advertises `"test": "vitest run"`.

**Fix:** import `assets/static/admin.js`, fix the fetch mocks (`ok: true`), add `npx vitest run` to `check.yml`, and de-duplicate the two `admin.js` copies.

### H8. CI pipeline: red type gate, unfailable migrations, and a deploy that skips the dependency bundle
**Area:** CI/deploy · `.github/workflows/check.yml:25, 69-75, 81-88` · *lead-verified*

(a) **`uvx ty check src/` (unpinned) now fails on main** — 2 errors at `src/main.py:2761` (D1 row `.get()` widens to `int | float | str | None`, rejected for `get_display_author(author: str | None, …)`). Runtime is unaffected; the unpinned tool drifted. The next CI run on any branch is red.
(b) **The migration step can never fail:** `… || { if echo "$?" | grep -qi "already exists" …` greps the *numeric exit code* for a string — never matches — so every failure (including a genuinely broken future migration) is swallowed as "may have already been applied", and the very next step deploys to production against a possibly un-migrated schema. The step also omits `--config wrangler.production.jsonc`.
(c) **The deploy step never builds `python_modules`** (zero references to it in either workflow), while `scripts/deploy_instance.sh:311-319` hard-fails without it and README step 2 calls it required. Either CI ships a worker missing its vendored deps, or the requirement documented in three places is false — the two deploy paths contradict each other.

**Fix:** pin ty (or fix the type at `main.py:2761`); grep wrangler's *output* (not `$?`) and fail the job on unrecognized errors; add the vendoring step (or document why production deploys don't need it).

### H9. README quickstart cannot produce a working instance
**Area:** docs/deploy · `README.md:56-119, 234-249`; `wrangler.jsonc:21, 66, 76, 95-104, 117-119`; `Makefile:64-67` · *lead-verified (names, migrations); agent-verified (rest)*

Followed literally, the quickstart fails at several steps:

1. **Step 3 creates `planetcf-*` resources; step 7 deploys root `wrangler.jsonc`, which binds `test-planet-db` / `test-planet-entries` / `test-planet-feed-queue|dlq`** (and is named `test-planet`). The deploy references resources the user never created; "update the database ID" covers only one of five mismatches. (The created names match `wrangler.production.jsonc` instead.)
2. **Step 4 applies only `migrations/001_initial.sql`.** Migrations 003/004 add `entries.first_seen` and `feeds.last_entry_at`, which the code writes unconditionally (`main.py:1205-1207`, `1237-1239`). Auto-init won't repair it (it only runs when the `feeds` table is absent, `main.py:432-436`), so every fetch fails with "no such column" — a fresh instance can never store an entry. The same single-migration instruction is replicated in `docs/MULTI_INSTANCE.md:143-146`, all four `examples/*/README.md`, the example wrangler comments, and `scripts/create_instance.py`'s generated output.
3. **Root config has `"crons": []`** — even a successfully deployed quickstart instance never fetches feeds automatically.
4. **Step 2 `make python-modules` is circular on a fresh clone:** it requires `.venv-workers/pyodide-venv` and tells you to run `uv sync` to create it, but `uv sync` doesn't (the workers tooling is in a non-default dependency group, and nothing invokes its builder).
5. **`npm install` doesn't install wrangler** (devDependencies: jsdom, vitest only), so `npx wrangler` ad-hoc downloads an unpinned version; the configs' `$schema` path into `node_modules/wrangler/` never exists.
6. The Development section's `wrangler d1 execute planetcf --local` references a database name that exists in no config.

**Fix:** point the quickstart at a config whose names match the created resources, instruct `for f in migrations/*.sql`, add wrangler to devDependencies, fix or document the `python-modules` bootstrap, and use a cron-enabled config.

### H10. `deploy_instance.sh` re-runs abort silently — its migration error-tolerance is dead code under `set -e`
**Area:** deploy scripts · `scripts/deploy_instance.sh:23, 269-296`; `migrations/003, 004` · *agent-verified empirically; bash semantics confirmed*

With `set -euo pipefail`, the failing command substitution in `OUTPUT=$(npx wrangler d1 execute … 2>&1)` exits the script before `EXIT_CODE=$?` is ever assigned, so the entire "already applied: duplicate column" tolerance is unreachable. Migrations 003/004 are bare `ALTER TABLE … ADD COLUMN` (non-idempotent; D1 errors on re-run), therefore **every re-run against an existing database dies at the migration step with no output** (wrangler's stderr was captured into the never-printed variable). The generated config's comment "The script is idempotent - safe to re-run" (`create_instance.py:430`) is false.

**Fix:** `if ! OUTPUT=$(…); then` (or `|| EXIT_CODE=$?`), echo the output on failure — and prefer consulting the migration ledger (see M11).

### H11. Every instance deployed by the tooling grants the upstream maintainer admin access
**Area:** trust/deploy · `migrations/002_seed_admins.sql:6-8`; `scripts/deploy_instance.sh:269` · *lead-verified*

`002_seed_admins.sql` hardcodes `INSERT INTO admins … VALUES ('adewale', 0, 'Adewale Oshineye', 1)`; `deploy_instance.sh` applies **all** migrations to every instance, and CI's loop applies it to production on every main push. Its comment ("generated from config/admins.json during deployment") is false — no generator exists. Any third party deploying a full-mode instance via the recommended script silently allowlists the upstream maintainer's GitHub account as an active admin. Combined with the unpinned `github_id` (see M-S4), this is also exposed to GitHub username recycling.

**Fix:** remove 002 from the generic migration set (seed via `scripts/seed_admins.py` or first-login bootstrap instead), or actually generate it per-instance.

### H12. Deterministic committed `SESSION_SECRET` protects a deployed, full-mode, publicly routable worker
**Area:** security/ops · `scripts/setup_test_planet.sh:35`; `scripts/seed_test_data.py:47`; `.github/workflows/e2e.yml:69` · *lead-verified*

`test-session-secret-for-e2e-testing-only` is committed in three places and installed as the real `SESSION_SECRET` of the deployed `test-planet` worker (full mode, real D1/Vectorize/queues, public `*.workers.dev` URL). `seed_test_data.py:169-179` itself demonstrates minting a valid admin cookie — anyone reading the repo can do the same against the live instance and use the entire admin API (add feeds → SSRF surface, OPML import, reindex, delete). Aggravating: **three configs share the worker name `test-planet`** (root `wrangler.jsonc`, `examples/test-planet`, and the "full-featured" `examples/planet-cloudflare`) and the same database id, so deploying the production-grade example overwrites the test worker and inherits the forgeable secret.

**Fix:** generate the test secret per-deploy (CI can create a random one and pass it to both the worker and the test env); give `planet-cloudflare` its own name/resources; consider Cloudflare Access in front of the test instance.

### H13. The documented lite-mode feed-management workflow does not exist
**Area:** docs · `docs/LITE_MODE.md:43-107`; `examples/*/config.yaml` (`initial_feeds`) · *lead-verified (grep)*

LITE_MODE.md instructs managing feeds by editing `assets/feeds.opml` or `config.yaml`'s `initial_feeds:` and redeploying ("New feeds are picked up on the next cron trigger… or on the next deployment"). **No code reads either** — `feeds.opml` matches only the OPML *export* route/templates; `initial_feeds` matches nothing in `src/` or the deploy script; the cron only enqueues rows already in D1. A user following the doc gets a permanently empty planet. The real path is `scripts/seed_feeds_from_opml.py`, which the doc never mentions. The same dead `initial_feeds` key ships in `examples/default/config.yaml` and `examples/planet-cloudflare/config.yaml` — directly under those files' own "changes have NO effect" warnings. Related: no example README mentions seeding at all, so even `deploy_instance.sh` yields an empty planet.

**Fix:** rewrite the section around `seed_feeds_from_opml.py` (or implement deploy-time OPML seeding, which the docs evidently believe exists).

### H14. Documented dev commands fail on a fresh clone; test claims stale
**Area:** docs/dev-experience · `README.md:241-242`; `Makefile:16-28`; `docs/TESTING.md:7-16` · *lead-verified (reproduced)*

`uv sync` does not install the `test` extra, so the README/Makefile/TESTING.md command `uv run pytest …` falls back to a system `pytest` on Python 3.11, which dies with `SyntaxError` on `class Ok[T]` (PEP 695). Required: `uv sync --extra test` (only CI and the "historical" SPEC.md get this right). Also stale: "~1200 tests, ~1.4s" (actual: 1,426 in ~28s; unit tier alone ~23s vs TESTING.md's "~2 seconds"). There is no `.python-version`/CI pin, so the interpreter under the suite is whatever the environment provides.

**Fix:** document `uv sync --extra test` (or move test deps to a default dependency-group), pin a Python version, refresh the counts (or replace with the `--co -q` command pattern TESTING.md already uses elsewhere).

### H15. Still no CSRF protection on any state-changing admin endpoint (prior finding #2 — open)
**Area:** security · `src/main.py:2885-2962`; `assets/static/admin.js` · *lead-verified (grep + enumeration)*

Unchanged since March: no CSRF token exists anywhere (the only "CSRF" in the codebase is the OAuth `state` parameter). All eleven state-changing admin endpoints rely solely on `SameSite=Lax` + (for JSON endpoints) content-type preflight behavior. The **form-POST** endpoints — add-feed, import-OPML, regenerate, DLQ retry, fetch-now, logout, `_method=DELETE` — are exposed to the Chrome Lax+POST 2-minute window and to any non-Lax-enforcing client. `form-action 'self'` in the CSP does not constrain a cross-site attacker's own page.

**Fix:** HMAC a per-session CSRF token (the signing infrastructure already exists in `auth.py`), embed it in admin forms and the `fetch` wrapper in `admin.js`, validate on every non-GET `/admin/*` request.

## Medium findings

### Pipeline & data
- **M-P1. Redirect target persisted before validation; all redirects treated as permanent; `UNIQUE(url)` collision unhandled.** `main.py:1089-1098` rewrites the stored URL before the HTTP ≥400 check and before parse succeeds: a temporary 302 to a maintenance page permanently replaces a good URL (auto-recovery then refetches the *broken* URL); two http/https variants of one feed collide on `UNIQUE(url)` and throw every cycle until auto-deactivation. Move the update after successful parse; handle the constraint failure. *(lead-verified)*
- **M-P2. Failure counting is per-attempt, not per-cycle.** Each failed attempt calls `_record_feed_error` *and* `message.retry()` (`main.py:1005-1014`); with `max_retries: 3`, one bad hour adds 4 failures, so `FEED_AUTO_DEACTIVATE_THRESHOLD=10` fires after ~2.5 hours of outage, not 10 cycles. `_fetch_feed_now` also lacks the `RateLimitError` branch the queue path has, so a 429 counts as a real failure.
- **M-P3. `SafeVectorize.deleteByIds` passes a raw Python list across the FFI** (`wrappers.py:438-440`), bypassing the project's own `_to_js_value` gate (the exact hardening from commit 7441e41 / lesson 29). If the binding rejects the PyProxy, the exception is swallowed in `_apply_retention_policy` (`main.py:2174-2185`) and D1 rows are deleted anyway — every retention cycle orphans vectors; the index grows and burns quota forever. Search stays correct only because D1 misses are dropped.
- **M-P4. Feed date formats violate the specs.** RSS `<pubDate>` emits the raw ISO DB value (`templates.py:1451`); Atom feed-level `<updated>` is `…+00:00Z` — offset *and* Z (`main.py:2378`); Atom `<published>{{ entry.published_at }}Z` renders bare `Z` for NULL dates and double-zoned values for clamped ones; entries lack the *required* Atom per-entry `<updated>`. Root cause: three `published_at` formats coexist in one column (`content_processor.py:145`, `main.py:1191`, `main.py:1207`), which also makes same-day `ORDER BY published_at` format-dependent. Normalize at write time; convert per-format at render.
- **M-P5. Health/audit data silently dropped at the FFI row factories.** `feed_row_from_js` (`wrappers.py:681-703`) whitelists columns and omits `last_entry_at`, `entry_count`, `last_error`; `audit_row_from_js` maps a nonexistent `admin_username` and drops the selected `github_username`/`display_name`. The health page therefore always renders "Last Entry: Never / Entries: 0" (`templates.py:681-683`), and the audit API can never attribute actions. *(agent render-verified)*

### Security (defense-in-depth)
- **M-S1. Feed-controlled URLs rendered into `href` with no scheme allow-list.** `entry.url` (`main.py:1221`) and `feed.site_url` (`main.py:1554-1577`) are stored unvalidated and rendered into anchors (`templates.py:58, 94, 182, 276, 852`). A feed advertising `<link>javascript:…</link>` produces a clickable stored payload; only the CSP (`script-src 'self'` governs `javascript:` navigation) prevents execution. Bleach's protocol allow-list covers content URLs only. Add a `safe_display_url()` (http/https/mailto, else `#`). *(lead-verified)*
- **M-S2. SSRF re-validation runs after the request; redirects auto-followed; DNS-based bypass unchecked.** The fetch wrapper uses `redirect: "follow"` (`wrappers.py:509`) and the final-URL check (`main.py:1071-1072`) happens after the body was downloaded — it blocks storing, not requesting; intermediate hops are never checked; `is_safe_url` only blocks IP *literals*, so a hostname resolving to 169.254.169.254 passes. Production exploitability is limited by Cloudflare's egress filtering; the httpx test path (`follow_redirects=True`) has no such net. Use manual redirect handling with per-hop validation, or document the reliance on the CF runtime.
- **M-S3. OPML XXE handling regressed from `forbid_dtd=True` to a first-DOCTYPE regex strip** (`admin.py:88-89`; `[^>]*` breaks on internal subsets containing `>`). Residual risk is low (stdlib ET resolves no external entities), but reject DOCTYPE/ENTITY outright instead of stripping. Note `docs/ARCHITECTURE.md:491` still claims `forbid_dtd=True`.
- **M-S4. Hardening tail:** admin identity keyed on username only — stored `github_id` is written but never verified, exposing admin accounts to GitHub username recycling (`main.py:2862, 3962-3969`); security headers missing on admin error pages / OPML / feeds / JSON (no `nosniff`, framable error pages — `admin.py:51-58`, `utils.py:232-259`); OPML import reads the whole upload before any byte cap (`main.py:3326-3339`); OAuth `redirect_uri` still falls back to request origin when the env var is unset (`main.py:3839-3852`).

### CI, tests, and tooling
- **M-T1. Coverage gate is timing-flaky.** Under `--cov` instrumentation, Hypothesis health checks fail (`test_properties.py:2294`, regex strategy draws >100ms; reproduced 2/2 locally). `check.yml:55` runs exactly this invocation — one slow runner from random red. Add a Hypothesis profile (`deadline=None`, suppress `too_slow`) for CI.
- **M-T2. E2E can be silently green.** All e2e modules skip at import when `E2E_BASE_URL` doesn't respond (verified: 107 skipped, exit 0); every `e2e.yml` step is `if: env.CLOUDFLARE_API_TOKEN != ''`; the browser job skips if `agent-browser` is missing. Nothing alerts when the whole tier evaporates. Fail the job if >N% skip.
- **M-T3. Mock fidelity.** Conftest `MockD1` validates neither bind-arity nor WHERE clauses (`.first()` returns the first row regardless of bound id; only a regex special-case for `is_active = <digit>`), so wrong-row/wrong-arity bugs pass unit tests — this is exactly why H3 was codified in a test rather than caught. The JsProxy-faithful `tests/mocks/d1.py` is imported by **zero** tests.
